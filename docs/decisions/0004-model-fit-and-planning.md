# 0004: Model catalog, memory fit, download estimates and run planning

Date: 2026-11-08
Status: accepted

## Context

Milestone (c) answers "which model and engine fit this machine, and what will it cost to get there?"
before anything is downloaded. The project rules (CONTRIBUTING.md) require every recommendation to
be measured or labeled an estimate, and ADR 0002 fixed the product defaults (quick first run of
about 5 GB). There is no registry of measurements yet, and engine adapters arrive in milestone (d).

## Options

- **Catalog data:** hand-typed sizes, or generated from the Hugging Face API with pinned
  revisions.
- **Weight memory:** parameters × bits per weight, or the measured size of the weight files.
- **Engine knowledge before adapters exist:** wait for (d), or write fixed per-engine rules now
  that the adapters reuse later.
- **HTTP client:** huggingface_hub 2.x moved from httpx to **httpx2** (the successor under
  pydantic/httpx2, BSD-3-Clause), and httpx has had no stable release since Dec 2024 (0.28.1).
  Options: use httpx2 directly; keep httpx alongside it (two clients); or pin huggingface_hub 1.x
  (still on httpx).

## Decision

- **Catalog** (`src/brasskey/models/catalog.yaml`):
  - Generated by `scripts/refresh_catalog.py` from the API: commit SHAs, file sizes, sha256,
    parameter counts, and architectures read from each base model's `config.json`.
  - Curated choices live in the script: the Qwen3 family 0.6B to 32B plus 30B-A3B
    (Apache-2.0, ungated, official repos for GGUF, MLX, BF16, FP8 and AWQ).
  - `pytest -m network` checks every pinned file upstream.
  - Any other repo works as `hf:org/name[:QUANT]`, labeled unverified.
- **Memory needed per device** = weight-file bytes / devices + KV cache share + engine overhead.
  - KV cache = bytes per token per layer × (full layers × context + sliding layers × window) ×
    concurrent sequences. MLA caches one latent, which is replicated across GPUs. KV heads shard
    until the tensor-parallel size exceeds them.
  - Mixture-of-experts active parameters are derived from the config (Qwen3-30B-A3B ≈ 3.35B).
- **Engine memory profiles (estimates, to be calibrated by measurement):**

  | Engine | Budget share | Fixed overhead | Share of weights |
  | --- | --- | --- | --- |
  | llama.cpp (Metal / CUDA) | 100% / 95% | 0.5 GiB | 2% |
  | llama.cpp (CPU) | RAM minus max(1 GiB, 15%); in a container, the limit minus 10% | 0.5 GiB | 2% |
  | MLX | 100% | 0.75 GiB | 5% |
  | vLLM | 90% | 2 GiB | 5% |
  | SGLang | 85% | 2 GiB | 5% |

- **Budgets:**
  - Apple: the GPU working-set limit (ADR 0003).
  - NVIDIA: the smallest GPU × engine share.
  - CPU: container-aware RAM minus the system reserve.
  - Free memory right now only produces warnings: it's transient.
- **Rules:**
  - Engine order: MLX → llama.cpp on Apple Silicon; vLLM → llama.cpp with NVIDIA GPUs on Linux;
    llama.cpp elsewhere. SGLang only on request.
  - NVIDIA minimums are conservative and get rechecked in (g): vLLM needs compute capability 7.0+
    (FP8 8.0+, AWQ 7.5+); SGLang 7.5+ (FP8 8.9+). BF16 below 8.0 runs as FP16, with a note.
  - Artifact: best quality that fits with ≥25% to spare, else best that fits. For vLLM/SGLang
    the order is BF16, FP8, AWQ.
  - Devices: the fewest that fit comfortably, else the fewest that fit, with tensor-parallel
    sizes that divide the attention heads.
  - Quick start: the most capable catalog model that fits comfortably with ≤5 GB still to
    download. Cached files don't count. Bigger fitting models are listed.
- **Download time:** measured with a ranged GET of the largest file, stopping at 8 MiB or after
  3 s. It matched `curl` on the same file (about 3 MB/s on the development link). It is skipped
  with `--offline` or `HF_HUB_OFFLINE`.
- **Speed:** "at most N tokens/s" = memory bandwidth / active weight bytes per token. It is
  shown as a ceiling, never as a promise.
- **HTTP client:** httpx2 (chosen by the founder on 2026-11-08); one client shared with
  huggingface_hub.
- **Privacy:** huggingface_hub telemetry is disabled before it loads, and its warnings and
  progress bars are silenced.

## Consequences

- Plans are reproducible for a given catalog version: same hardware, same catalog, same plan.
  Download time is the one measured, variable part.
- Engine overheads and the macOS limit are the weakest numbers. Milestones (d), (e) and (g)
  should record measured memory after a successful start and replace these defaults.
- On large GPU servers the quick-start choice stays small (download cap); the plan lists the
  bigger models and users name one.
- Refreshing the catalog is a deliberate, reviewed change (script, diff, tests, network check).
