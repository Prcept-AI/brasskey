# 0012: Release pipeline

Date: 2026-11-08
Status: accepted (not yet run against PyPI: needs the trusted publishers and environments in
RELEASING.md)

## Context

`pip install brasskey` and `uv tool install brasskey` are the v0.1 install channels (ADR 0002).
The project rules (CONTRIBUTING.md, supply chain) ask for:

- trusted publishing with no long-lived tokens;
- signed releases, an SBOM and checksums;
- every tool pinned.

Python projects have had their PyPI tokens stolen through compromised CI tools, so the release
path is part of the product.

## Options

- **Publishing:** an API token in a GitHub secret, or PyPI trusted publishing (OIDC: PyPI trusts
  one workflow in one repository, and there is nothing to steal).
- **Signing:** separate `.sigstore` bundles, or what trusted publishing and GitHub already sign.
  The second covers PEP 740 attestations on PyPI and GitHub artifact attestations for build
  provenance.
- **README on PyPI:** absolute links in README.md (images break on GitHub while the repository is
  private), a second README for PyPI (two copies to keep in sync), or a build hook that rewrites
  the links for the package metadata only.

## Decision

- **`.github/workflows/release.yml`:**
  - A tag `v<version>` publishes to PyPI; running the workflow by hand publishes to TestPyPI as a
    rehearsal.
  - Jobs:
    1. build;
    2. provenance (public repositories only);
    3. publish (in the protected `pypi` / `testpypi` environment);
    4. GitHub release.
  - Each job gets only the permissions it needs, with a comment saying why. No caches. Every
    action is pinned by commit SHA, and Syft by version. All of them passed the 7-day cooldown.

  | Action | Version | License |
  | --- | --- | --- |
  | pypa/gh-action-pypi-publish | v1.14.3 | BSD-3-Clause |
  | actions/attest-build-provenance | v4.2.2 | MIT |
  | anchore/sbom-action (Syft v1.55.0) | v0.24.3 | Apache-2.0 |
  | actions/upload-artifact | v7.0.2 | MIT |
  | actions/download-artifact | v8.0.2 | MIT |

- **Builds:**
  - `uv build`, with the build backend (hatchling and its dependencies) pinned by hash in
    `scripts/build-constraints.txt` (`--require-hashes`).
  - `SOURCE_DATE_EPOCH` = the commit time, so builds are reproducible. Every build is done twice
    and compared, in CI on every push and in the release.
- **Checks** (`scripts/check_dist.py`, standard library only):
  - exactly one wheel and one sdist, with the same version, which must equal the tag;
  - the package data and license files are present, and the wheel holds no tests;
  - `License-Expression: Apache-2.0`;
  - the description has only absolute links;
  - the sdist holds only an allowlist of top-level entries, so nothing else in the working folder
    can ship.

  Then the wheel is installed into a clean environment and run.
- **SBOM:** Syft scans an environment holding the locked runtime dependencies (hash-checked) and
  the wheel. The result is SPDX 2.3 JSON with 42 packages, each with its license.
- **Checksums:** `SHA256SUMS` for the wheel and the sdist.
- **README on PyPI:** `hatch_build.py`, a hatchling metadata hook, makes the README's relative
  links absolute. They point at the version's tag: images to raw files, folders to trees, files to
  blobs. README.md itself stays relative.
- **Verification for users:** SECURITY.md covers checksums, `gh attestation verify`, rebuilding
  from the tag, and the PyPI attestations.

## Consequences

- No new runtime or development dependencies. CI adds a packaging job of about a minute on Linux.
- The first PyPI upload needs a maintainer to configure trusted publishing on pypi.org and
  test.pypi.org, and the GitHub environments (RELEASING.md). Until the first upload, the name
  isn't reserved.
- Build provenance is skipped while the repository is private.
- `scripts/build-constraints.txt` is regenerated by hand when the build backend changes (the
  command is in its header); Dependabot doesn't update it.
- Later: brew, Docker image and install script channels, each with the same signing and SBOM
  rules.
